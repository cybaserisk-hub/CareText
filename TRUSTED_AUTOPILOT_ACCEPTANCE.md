# Trusted Autopilot: first-release acceptance criteria

Required for release one, **disabled now**. This document is an acceptance contract. Offline development controls are implemented in `src/autopilot-controls.mjs` with transactional PGlite tests; production integration is NOT complete. `architecture/src/eligibility.mjs` is a design starter, not trusted production authorization. The database still permits only manual/paused modes. No worker, activation endpoint or AI integration is enabled by this preparation.

## Consent contract

New invitations use `caretext-sms-consent-v3` and disclose BOTH standard subscriber-approved CareTouch and automatic AI generation/delivery under eligible, explicitly opted-in Trusted Autopilot after 90 days. Recipient consent and subscriber mode selection are separate decisions. Consent does not turn on Autopilot or bypass any gate.

Preserve exact historical disclosure, version, timestamp, schedule and provider evidence. v1, v2, unknown and simulated evidence do not authorize Autopilot. Existing recipients need a new v3 invitation, fresh verification and affirmative acceptance before Autopilot use. Do not UPDATE old evidence, backdate consent or relabel records. A declined or expired re-consent does not expand the prior grant. Changing recipient/number or materially changing the disclosed schedule requires renewed consent. Owner-approved decision: record explicit subscriber opt-in and queue subscriber in-app and email mode-change confirmations. Do not require an extra recipient mode-change notification unless final compliance review requires one. The original v3 grant covers both models; prior narrower consent still requires re-consent.

The current server delivery guard checks model coverage and remains unconditionally blocked by `delivery_allowed=false`. `consentCoversModel` is only a scope check; it is not Autopilot eligibility authorization.

Recovery must never reactivate by bulk SQL or automatically resume after a provider incident; explicit revalidation/resume is required. Off-limits changes require renewed sample review as specified in the design.

## Decisions and release exit

Owner has approved Auth account creation plus 90 elapsed days, two completed human-approved batches, subscriber in-app/email confirmations, 08:00–21:00 recipient-local delivery, no outage catch-up, and explicit authorized resumption only after all checks. Platform content policy/evaluation thresholds and production evidence integration still need completion. These are implementation decisions, not requests to enable anything now. Final delivery requirements also include A2P approval, verified provider routing, secure secrets, production quotas, completed retention/restore work and independent sending approval. All A01-A16 evidence must pass before activation can be approved; time passing alone never enables the feature.

## Development verification limits

The test-only transaction store is explicitly loaded from `tests/fixtures/migrations/20261021045006_autopilot_preparation.sql`; it is not in the hosted migration queue. Its snapshots are synthetic and do not confer production authority. Production `autopilot_settings` remains restricted to manual/paused. `LIVE_AUTOPILOT_ENABLED` is false and `liveSubmit()` always rejects; no environment switch bypass exists.

Safety checks require a content-hash, relationship, revision, five-minute freshness, audit ID and explicit pass for every reviewed category. Missing/uncertain checks suspend. This verifies the attestation contract, NOT semantic safety: a trusted evaluator, curated multilingual/adversarial evaluations, policy thresholds and securely bound audit records remain required. A caller-supplied all-pass object must never be accepted from a browser.

Production wiring remains a development blocker, not merely an approval: authoritative consent/subscription/preferences/batch loaders, atomic live consent and quota locks, server event triggers, scheduled slot provenance, subscriber controls/activity view, delivered confirmation outbox, production content evaluators and provider reconciliation. The local simulation does not prove multi-process PostgreSQL races, provider timeout reconciliation, semantic filtering or hosted deletion. Do not describe A01–A16 as production-complete.
