# Trusted Autopilot: first-release acceptance criteria

Required for release one, **disabled now**. This document is an acceptance contract, not a claim that Autopilot is implemented. `architecture/src/eligibility.mjs` is a design starter, not trusted production authorization. The database still permits only manual/paused modes. No worker, activation endpoint or AI integration is enabled by this preparation.

## Consent contract

New invitations use `caretext-sms-consent-v3` and disclose BOTH standard subscriber-approved CareTouch and automatic AI generation/delivery under eligible, explicitly opted-in Trusted Autopilot after 90 days. Recipient consent and subscriber mode selection are separate decisions. Consent does not turn on Autopilot or bypass any gate.

Preserve exact historical disclosure, version, timestamp, schedule and provider evidence. v1, v2, unknown and simulated evidence do not authorize Autopilot. Existing recipients need a new v3 invitation, fresh verification and affirmative acceptance before Autopilot use. Do not UPDATE old evidence, backdate consent or relabel records. A declined or expired re-consent does not expand the prior grant. Changing recipient/number or materially changing the disclosed schedule requires renewed consent. Sender enabling Autopilot must also satisfy the existing architecture requirement for a recipient mode-change disclosure; define and verify that notification before activation, with sending separately approved.

The current server delivery guard checks model coverage and remains unconditionally blocked by `delivery_allowed=false`. `consentCoversModel` is only a scope check; it is not Autopilot eligibility authorization.

## Release-blocking acceptance matrix

All requirements below need trusted server records, audit evidence, unit/integration tests and isolated end-to-end acceptance. Missing/unknown/stale values fail closed. A frontend toggle or user metadata must never confer eligibility.

| ID | Required behavior | Required tests and evidence | Current status |
| --- | --- | --- | --- |
| A01: 90 days | Follow the existing architecture's account-age rule: server UTC elapsed time from immutable Auth account creation, at least 90 x 24 hours; never browser clock or lazily created profile time. Confirm this clock definition before implementation | 89d23h59m59s denied; exact boundary eligible only if every other gate passes; future/missing timestamp and clock manipulation denied | Criteria prepared; runtime absent |
| A02: subscriber preparation | Preserve design prerequisite of at least two completed human-approval cycles and no unresolved consent/delivery issues. Derive cycles from immutable approved batches, not clicks | Duplicate/retried approvals count once; incomplete cycles and unresolved incidents block | Runtime absent |
| A03: verified recipient | Current, unwithdrawn v3 scope for exact sender/recipient/relationship/phone, valid provider evidence, unchanged disclosed schedule; no suppression | v1/v2/unknown/test evidence denied; phone edit, STOP, withdrawn or superseded grants block; new v3 consent does not mutate old evidence | Scope/consent tests pass locally; hosted checks pending |
| A04: paid subscription | Trusted active Essential/Plus subscription; Free, missing, inactive, past_due and cancelled blocked; recheck before enqueue and provider submission | Plan downgrade/cancellation/payment-event races and stale cache; no client write to subscriptions | Basic consent eligibility tested; dispatch absent |
| A05: recipient limits | Essential one, Plus five active relationships; retain rolling 30-day voluntary replacement rule and documented exceptions | Concurrent activation at capacity, replacements across accounts, sender isolation | Basic local consent tests pass; real concurrency pending |
| A06: schedule/frequency | Saved recipient-consented timezone/schedule only; Plus-only Daily; at most one planned outgoing message/day/relationship, bounded by quota. No spontaneous schedule or recipient changes | DST transitions, timezone changes, missed slots, duplicate cron/retry, schedule revision; no catch-up burst | Dispatcher absent |
| A07: quota | Atomic account-wide reservation against 15 Essential / 100 Plus monthly SMS allocation, shared across both modes; define and enforce encoded segment accounting before launch | Concurrent workers, GSM/Unicode segmentation, retry idempotency, boundary/reset with actual billing period; uncertain provider result must not free capacity and resend blindly | Not implemented |
| A08: explicit subscriber opt-in | Separate unchecked relationship-specific control after eligibility; record actor, server time, version and approved profile/off-limits revisions. Initial signup, payment, recipient consent, age or page reload never enables mode | Unchecked, forged, cross-sender, stale revision and replay denied; changing browser/localStorage values ineffective | Not implemented |
| A09: topic/content controls | Enforce subscriber/recipient off-limits topics plus reviewed platform safety rules on each generated message. Treat examples/replies as untrusted data; never instructions. Check prohibited content, sensitive inferences, repetition, fabricated events and inappropriate claims; no secrets/other recipients in context | Curated adversarial and benign eval set, prompt injection, multilingual/obfuscated topics, stale settings, missing filter, model timeout and malformed output; fail closed on uncertainty | Provider and evaluation policy pending; no AI calls |
| A10: revision changes | Sensitive preference, LearnMe or off-limits changes pause Autopilot and invalidate queued content generated from old revisions; require reviewed samples and explicit resume | Concurrent edit/generation/dispatch, old worker result, old opt-in replay | Not implemented |
| A11: manual override | Subscriber can return to manual approval at any time; queued unapproved Autopilot work canceled. Manual text is an immutable approved snapshot, still subject to consent, safety, schedule and quota | Edit after approval invalidates approval; operator override cannot bypass STOP, cap or consent | Not implemented |
| A12: pause/disable | Relationship and account pause plus global kill switch; durable state, visible reason, immediate prevention of new dispatch; no auto-resume after refresh/restart | Pause while generating, queued, retrying and before provider submission; failed persistence blocks sending | Not implemented |
| A13: automatic suspension | Safety failure, unknown consent/subscription state, provider/auth error, missing audit or rate data, queue inconsistency, unsupported model response or unresolved incident suspends affected work and records reason; global outage can suspend all | Simulated unavailable DB/provider/safety service, revoked credentials and missing configuration; no fallback that bypasses checks; supervised recovery revalidates all gates | Not implemented |
| A14: final delivery gate | One atomic reservation/idempotency path for both modes; live consent/suppression/version/plan/pause/safety recheck immediately before submission. A STOP concurrent with work wins before submission | Multi-connection races, duplicate jobs/callbacks, timeout-after-provider-acceptance, durable dedup and reconciled status; prove no duplicate sends | No sender/worker exists |
| A15: inbound behavior | Autopilot never automatically replies, changes recipients or schedules based on inbound text. Signed STOP/HELP preserved; ambiguous multi-sender replies remain private | Instruction-like reply cannot activate mode or alter settings; signature failure makes no mutation; ambiguous content never leaks | Signed routing tested locally; live callbacks pending |
| A16: notices and audit | Mode-change notice, opt-in, profile revisions, generated-content approval/safety decisions, queue reservations, provider outcomes and suspension actions attributable and minimal; do not log phone/code/token/body to general logs | Audit write failure blocks dispatch; privacy/deletion and authorized access tests; subscriber activity view and support escalation | Not implemented |

STOP/withdrawal prevent future authorized sends, but an SMS already submitted to a carrier may not be recallable. Do not promise zero in-flight delivery. Recovery must never reactivate by bulk SQL or automatically resume after a provider incident; explicit revalidation/resume is required. Off-limits changes require renewed sample review as specified in the design.

## Decisions and release exit

Owner confirms the existing account-age clock and two-cycle criterion, the platform content policy/evaluation thresholds, mode-change notice channel/text, quiet-hour/timezone defaults, suspension escalation and approved resumption procedure. These are implementation decisions, not requests to enable anything now. Final delivery requirements also include A2P approval, verified provider routing, secure secrets, production quotas, completed retention/restore work and independent sending approval. All A01-A16 evidence must pass before activation can be approved; time passing alone never enables the feature.
